# 01: Plan acceptance evidence and submission

**What to build:** Create the Phase 2 acceptance-to-evidence matrix and submission outline before feature development. Each later ticket must have a defined place to record its automated tests and any production check, screenshot, or screencast evidence required for the university submission.

**Blocked by:** None (can start immediately).

**Status:** ready

## Acceptance criteria

- [ ] The repository contains an acceptance-to-evidence matrix that traces committed-core requirements and each stretch path separately.
- [ ] Each matrix entry can record its source requirement, owning ticket, automated test, production check, screenshot or screencast need, completion state, and artifact location.
- [ ] The matrix distinguishes evidence planned during implementation from evidence captured from the final Railway deployment.
- [ ] The submission outline covers the nine Phase 2 slides, annotated screenshots, final technology choices, architecture, Phase 1 changes, tests, CI, accessibility, Railway deployment, reflection, and embedded screencast.
- [ ] The outline records the public repository URL, required presentation filename, 100 MB limit, and PebblePad submission checks.
- [ ] Tickets 02 through 20 are required to update the matrix before they can complete.

## Implementation tasks

- [ ] Add the acceptance-to-evidence matrix and define its completion and artifact-link conventions.
- [ ] Add the Phase 2 submission outline with placeholders for the final stretch decisions and Phase 3 deferrals.
- [ ] Record that final screenshots must come from Railway and include the deployed commit and capture date.
- [ ] Record the clean-source and annotated-image workflow, including which artifacts stay in the repository and which stay in the course Drive folder.
